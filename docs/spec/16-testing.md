## 16. Testing

- **Backend (real PostgreSQL, separate test DB, truncate between tests; no SQLite):** domain unit tests; repository integration tests (bulk insert, dedupe, visit assignment, concurrent batches for one visitor produce one visit, chunking); API tests for validation, authn/authz, and **tenant isolation**: two organizations with real IDs, where User B gets `404` (identical body to a missing resource) on **every** route touching org A's resources, including stats, management, exports, share links, and diagnostics; the route-coverage test (section 11); project-member scoping (an org `member` without a `project_members` row sees nothing, a `viewer` gets `403` on admin actions for a project they can see); platform admin who is not a member gets `404` on tenant data; last-owner removal/demotion rejected; a write key from project A cannot write to B; server-key events create no visit and are excluded from visitor/bounce metrics; `$revenue` without `$currency` is dropped; revenue never summed across currencies; route templates (matching, ordering, ReDoS-safe inputs, preview endpoint); `pages_seen` cap and `/__other__` overflow; diagnostics cardinality stays bounded under a flood of random origins; oversized and malformed payloads; skew correction and age/future rejection; retry-duplicate behavior; aggregation boundaries (range edges, DST transitions in the reporting time zone, midnight UTC visitor rotation); filter-injection attempts; transaction rollback on mid-batch DB failure leaves no partial state; auth tests (timing-equalization path executes, rotation on login, revocation, idle/absolute expiry, CSRF origin rejection, TOTP replay rejection, invite single-use).
- **Nest + Vitest:** decorators and metadata require an SWC-based transform; configure and verify it works before writing tests.
- **SDK:** section 8.7.
- **Frontend:** component tests for filter bar, date range, breakdown table, error/empty/403 states; protected-route behavior; URL ↔ filter state; project switching; API error normalization.
- **E2E (Playwright, real API + DB + built SPA):** log in → create project → copy key → example app sends a page view and a custom event → dashboard shows both → viewer cannot reach management → second project cannot see first project's data → share link shows read-only data.
- **Load tests (`tools/load`):** scripts for sustained ingestion, burst, mixed ingestion + stats, and abusive input. Record hardware, PostgreSQL settings, pool size, batch size, and duration with every result. Measure accepted events/s, p50/p95/p99, error and rejection rates, DB insert throughput, pool utilization, stats query latency, RSS under sustained load. Do not publish numbers that were not measured. Set initial targets from the **first measured baseline**, then identify the bottleneck before optimizing anything.
- Inspect and record `EXPLAIN (ANALYZE, BUFFERS)` for each stats query against a seeded dataset of at least 10 M events (generate with a script in `tools/`).
